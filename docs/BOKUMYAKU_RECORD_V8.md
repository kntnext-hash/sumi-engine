# 墨脈 — 育成後の記録構成 v0.8検証

基点03628c2、2026-10-22。現行製品v0.7/rules3のG-V7-04を対象とする。ゲーム以外の描画・Sceneは変更しない。

## 事前条件

- 第1候補はRecordの枝強化上限6→9のみ。Supply >= 2×次枝Lv、Damage >= 次枝Lv、購入費用、毎秒購入枠を維持する。候補は最大3案、採用後に追加調整をしない。
- 初期meta0と固定育成meta（Damage/Supply/Growth/Harvest = 14/13/14/12）を分け、同seed/同武器/BalancedでFarming対Recordを比較。seed1..10、6武器。固定育成点は旧v0.6の19周測定由来で、新版の連続育成試験ではない。
- 初期G04はPoint深度/効率各8/10、全武器各48/60、各武器6/10以上を維持。育成後にも同じ閾値を別途適用する。引分は勝ちに数えず、平均Wave差も報告する。
- 効率は通常結晶×60/(戦闘秒+再出撃待機3秒)。初達成報酬は含めない。Farmingの基準版と候補版が一致することを確認する。Recordだけの変更でG05の45/50を合格に変更しない。
- 採用候補を固定した後、seed11..20で追加確認する。既知seed/武器での未達を隠すための対象除外はしない。

## 診断と互換

枝の購入Lvと実際の先端数は同じではない。枝ノード64上限、成長タイミング、供給分散を確認し、上限増加が実際に戦闘へ寄与したかを調べる。

採用する戦闘変更は新規周回へ版を付けて適用し、進行中のrules1/2/3は従来計算を保つ。変更前実Unity DLLからseed42・上記育成点のFarming/Record、6000/6900tick/終端をlogs/v7-fixturesに採取した。採用時にはfixtureをテストへ追加し、未来と終端の一致を検証する。

数値試験・Unityコンパイル/NUnit・画面操作・Windows Player・実機を混同しない。今回の結果は後段およびQA台帳へ追記する。

## 第1候補と残りの比較仮説

枝上限のみの案は120 Record条件すべて終端不変。育成後も供給Lv12〜13で終了し、枝Lv7の条件Supply14に届かない。上限だけを増やす案は採用しない。

この観測に基づき残り2案を固定する。Bは枝Lv6以降、攻撃条件が足りていれば次枝に必要な供給を優先購入する。CはRecordの通常cycle内のBleed枠をSupplyへ置換する。両案とも枝上限9、既存供給/攻撃条件・費用・購入周期を保持。他の敵/報酬/戦闘計算は変えない。計3案で比較を終了する。

## 結果・限定採用

|案|初期G04|育成Pointの旧Record比平均Wave差|判断|
|---|---|---|---|
|A 上限のみ|維持（全条件不変）|0|不採用、条件未到達|
|B 後半の供給優先|維持（全条件不変）|+2.6|限定改善として採用|
|C 通常cycleの滲墨→供給|未合格|−1.6|不採用、初期も悪化|

Bの選定用seed1..10では育成Recordが旧版に深度で退行した条件は0。Pointは10/10改善したが、対Farmingでは5勝5同点（平均+1.2Wave）でありG-V7-04未合格。育成Farmingの効率優位は60/60維持。seed1/Pointでは枝Lv7をtick16530、Lv8を17400、Lv9を18390で購入し、実先端10→11→12に到達した。ノードは24→26→28で上限64は阻害しなかった。

固定後seed11..20でもPointは旧Record比10/10改善、平均+2.1Wave。ただしBleed seed18は57→56Waveの退行が1件あった。全条件改善とは言わず、主要Pointの再現した改善として採用する。追加候補や再調整はしない。

初期G04は既定seed1..10では深度56/60・効率55/60を維持したが、追加11..20は深度42/60（Enso5/10）、効率58/60。これは基準版も同じで、今回の変更による悪化ではないが、広いseedでの役割保証は未合格。

育成Sweep/Ensoでは両構成とも60Wave上限へ到達し、厳密な深度優位を判定できない。上限同着を勝ちへ変更しない。長期コンテンツの上限と、上限未到達武器の購入配分を次の別課題とする。Recordだけの変更で初回尺G05を解消扱いにしない。

実装は新規rules4。旧rules1〜3は従来購入順、保存先はcampaign-v5（ファイル世代5、JSON schema3/configv3）へコピー移行する。旧v4/v3/v2/v1原本・bakは保持する。測定ソースと製品ソースの一致、Unity・Player検証結果はQA台帳に記録する。
